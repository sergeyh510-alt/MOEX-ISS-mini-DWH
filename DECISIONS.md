# Журнал технических решений (DECISIONS)

Документ фиксирует только те решения, которые уже реализованы в коде, и
причину каждого выбора. Разделы идут по этапам проекта (1-7); каждый этап
опирается только на то, что реально есть в репозитории.

## Этап 1. Каркас и запуск стека

### 1.1. Версия Airflow - 2.7.0, как в проекте-образце

**Решение:** базовый образ `apache/airflow:2.7.0-python3.10`, Airflow 2.7.0.

**Почему:** версия взята без изменений из референсного проекта
`Mteo_Weather_AirFlow` (в нём используется `apache/airflow:2.7.0`), чтобы
сохранить единый проверенный стек и не смешивать два разных набора API Airflow.
Тег образа намеренно не обновляется в рамках этого этапа.

### 1.2. Отдельная БД для метаданных Airflow и для мини-DWH

**Решение:** два сервиса PostgreSQL 15:
`airflow_postgres` (метаданные Airflow) и `dwh_postgres` (мини-DWH).

**Почему:** метаданные Airflow и бизнес-данные DWH имеют разные жизненные циклы.
Разделение исключает случайную запись ETL-кода в служебные таблицы Airflow и
позволяет очищать/пересоздавать DWH независимо от состояния Airflow.

### 1.3. LocalExecutor, а не CeleryExecutor

**Решение:** `AIRFLOW__CORE__EXECUTOR=LocalExecutor`, сервис `redis` отсутствует.

**Почему:** для учебного проекта на одном узле LocalExecutor проще: не нужны
redis и worker'ы. Это отклонение от образца (там присутствует redis), но оно
осознанное и упрощает стек.

### 1.4. Отдельный одноразовый сервис `airflow-init`

**Решение:** миграции метаданных (`airflow db migrate`) и создание
администратора выполняет отдельный сервис `airflow-init`, а `airflow-webserver`
и `airflow-scheduler` стартуют после его успешного завершения
(`condition: service_completed_successfully`).

**Почему:** так `docker compose up` с чистого клона воспроизводим и без ручных
шагов: инициализация выполняется один раз, а долгоживущие сервисы получают
готовую схему метаданных. В образце инициализация была встроена в команду
запуска webserver (`db init` + `users create` + `webserver & scheduler`), здесь
это разделено для предсказуемости.

### 1.5. Схемы DWH создаются при инициализации тома и идемпотентны

**Решение:** файл `sql/00_schemas.sql` смонтирован в
`docker-entrypoint-initdb.d` и выполняет `CREATE SCHEMA IF NOT EXISTS` для
`raw, stg, core, mart, meta, audit`.

**Почему:** Postgres применяет скрипты из `docker-entrypoint-initdb.d` только
при инициализации пустого каталога данных. `IF NOT EXISTS` делает скрипт
безопасным и позволяет применять его повторно (например, из DAG'а на уже
существующем томе).

### 1.6. Секреты только через .env

**Решение:** в репозитории лежит `.env.example`; сам `.env` добавлен в
`.gitignore`. `docker-compose.yml` подставляет значения через
`${VAR:-default}`, поэтому запуск без `.env` также возможен.

**Почему:** исключает попадание паролей и ключей (в т.ч. `FERNET_KEY`) в git.
Значения по умолчанию - заведомо dev-заглушки, не предназначенные для прода.

### 1.7. Проверка доступности MOEX ISS вынесена отдельно

**Решение:** `scripts/check_moex.py` - необязательный ручной скрипт.

**Почему:** недоступность внешнего API не должна ломать запуск стека и DAG'ов;
проверка выполняется по требованию и не входит в состав пайплайна.

### 1.8. Порты и имена контейнеров настраиваются, а не задаются жёстко

**Решение:** в `docker-compose.yml` нет `container_name`, а все хостовые порты
задаются переменными (`AIRFLOW_WEB_PORT`, `AIRFLOW_PG_HOST_PORT`,
`DWH_PG_HOST_PORT`). В служебных командах используется `docker compose exec
<service>` по имени сервиса, а не по имени контейнера.

**Почему:** на машине параллельно работает второй стек (`Mteo_Weather_AirFlow`),
который занимает 8080 и 5434. Жёсткие `container_name` давали конфликт имён
контейнеров, а жёсткие порты - конфликт привязок. Значения по умолчанию
безопасны для чистой машины, локальные переопределения живут в `.env`.

## Этап 2. Слой raw: клиент MOEX ISS и идемпотентная загрузка

### 2.1. Полная строка ответа ISS сохраняется в JSONB

**Решение:** таблицы `raw.moex_history` и `raw.moex_index_history` хранят
ключевые поля отдельными колонками, а исходную строку целиком - в `row_json`.

**Почему:** набор колонок в API может отличаться от ожидаемого. Явные колонки
дают удобные запросы и ключ, а `row_json` гарантирует, что ничего не потеряно.

### 2.2. Идемпотентность raw через ON CONFLICT DO NOTHING

**Решение:** натуральный ключ (`boardid`, `secid`, `tradedate`) закреплён
первичным ключом; вставка идёт через `ON CONFLICT DO NOTHING RETURNING 1`.

**Почему:** повторная загрузка за ту же дату не создаёт дублей. Дубли внутри
одной пачки дополнительно снимаются перед вставкой (`deduplicate_rows`),
потому что Postgres не допускает конфликтов между строками одного `INSERT`.

### 2.3. Число реально вставленных строк считается по RETURNING

**Решение:** результат запроса с `RETURNING 1` подсчитывается функцией
`count_returned`, учитывающей разбиение `execute_values` на страницы.

**Почему:** `cursor.rowcount` для многостраничной вставки не отражает общее
число строк; `RETURNING` даёт точный счётчик и корректно работает с
`ON CONFLICT DO NOTHING`.

### 2.4. Слой raw не тянет Airflow

**Решение:** `include/raw_loader.py` и `scripts/load_raw.py` не импортируют
Airflow; CLI-скрипт запускается и из контейнера, и из DAG-задачи.

**Почему:** код тестируется и переиспользуется вне Airflow, а DAG остаётся
тонкой обёрткой над точкой входа.

### 2.5. Ретраи HTTP вынесены в сессию requests

**Решение:** `MoexIssClient` использует `HTTPAdapter` + `Retry` с backoff и
списком статусов; параметры (`BASE_URL`, размер страницы, таймаут, число
ретраев, backoff) читаются из переменных окружения.

**Почему:** временные ошибки ISS не должны ронять задачу, а поведение клиента
настраивается без правки кода.

## Этап 3. Слой stg: типизация, качество, справочник

### 3.1. Строки не удаляются, а помечаются (is_valid + reject_reason)

**Решение:** `stg.stock_history` и `stg.index_history` содержат `is_valid`
и `reject_reason`; невалидные строки остаются в stg.

**Почему:** отбраковка аудируема и воспроизводима, а решение о фильтрации
принимает слой `core`. Правила проверок (пропуск OHLC, неположительная цена,
`high < low`, `high` вне диапазона open/close, отрицательные счётчики) -
внутренние правила проекта, они описаны в `include/stg_rules.py`.

### 3.2. Идемпотентность stg через ON CONFLICT DO UPDATE

**Решение:** построение stg идёт upsert'ом по натуральному ключу
(`boardid, secid, tradedate` и `index_code, tradedate`) с перезаписью
`sources`-колонок и `updated_at`.

**Почему:** повторное построение за период не создаёт дублей, но подтягивает
изменения из raw. Ключ и колонки обновления фиксированы, `updated_at`
показывает, когда строка менялась.

### 3.3. Справочник бумаг - SCD1 из данных торгов

**Решение:** `stg.securities` (ключ `secid, boardid`) хранит `shortname`,
первую и последнюю дату торгов; заполняется агрегатом из raw и обновляется
upsert'ом.

**Почему:** отдельного эндпоинта справочника бумаг на этом этапе не
используется, а данные торгов уже дают корректный справочник. SCD1 выбран
сознательно: история переименований не требуется. Это отмечено в коде как
задача следующих этапов.

### 3.4. Счётчики stg пишутся в тот же журнал meta.load_run

**Решение:** `meta.load_run` расширен колонкой `rows_rejected`; задачи stg
пишут в журнал `rows_loaded` и `rows_rejected`.

**Почему:** журнал загрузок остаётся единым для всех слоёв, а число
отбракованных строк видно без запросов к stg.

### 3.5. DDL выделен в отдельный модуль и один список скриптов

**Решение:** `include/sql_init.py` применяет `00_schemas, 10_raw, 20_stg,
50_meta` по порядку; модуль вызывается из CLI (и будет вызываться из DAG).

**Почему:** объекты слоёв создаются идемпотентно на любом томе (на чистом томе
их создаёт `docker-entrypoint-initdb.d`, на существующем - этот вызов), а
`raw_loader` перестал зависеть от DDL-деталей.

## Этап 4. Слой core: звезда

### 4.1. Разделение на измерения и факты с суррогатными ключами

**Решение:** `core.dim_security` (ключ `security_key`, IDENTITY), `core.dim_date`
(ключ `date_key` = YYYYMMDD), факты `core.fact_daily_prices`
(`security_key, date_key`) и `core.fact_daily_index` (`index_code, date_key`).

**Почему:** суррогатные ключи дают привычную звёздную модель и дешёвые джойны,
а `date_key` как целое YYYYMMDD - стандартный и читаемый ключ календаря.

### 4.2. Измерения - SCD1, ключ не меняется

**Решение:** `dim_security` обновляется upsert'ом по естественному ключу
(`secid`, `boardid`); строка одна, `security_key` выдаётся один раз.

**Почему:** связи фактов с измерением должны быть стабильны между запусками.
Если бы ключ пересоздавался, повторный прогон ломал бы ссылки факта, поэтому
SCD1 с неизменным суррогатным ключом здесь честнее, чем delete+insert.

### 4.3. dim_date наполняется за календарный период и обновляется с guard

**Решение:** `build_dim_date` вставляет календарные дни за период
(`ON CONFLICT (date_key) DO NOTHING`), затем пересчитывает `is_trading_day`
по данным stg. В `UPDATE` есть guard `is_trading_day IS DISTINCT FROM (...)`.

**Почему:** дни должны существовать для всего периода фактов (включая выходные
и праздники), а guard делает повторный запуск no-op - строки и `updated_at`
не меняются без реальной необходимости.

### 4.4. Факты считаются upsert'ом, изменение цены - к прошлому торговому дню

**Решение:** `fact_daily_prices`/`fact_daily_index` заполняются upsert'ом по
составному ключу; `prev_close` берётся через `LAG(close)` по всей истории stg
(не только по периоду запуска), `close_change` и `close_change_pct`
(округление до 4 знаков) считаются от него.

**Почему:** upsert по ключу проще и дешевле delete+insert и даёт идемпотентность
без пересоздания всей звезды; окно `LAG` по всей истории нужно, чтобы первая
дата периода тоже получила корректный `prev_close`.

### 4.5. В core попадают только валидные строки stg

**Решение:** выборки в `core_builder` содержат `WHERE is_valid`.

**Почему:** отбраковка живёт в stg (и остаётся аудируемой), а core - это уже
доверенные данные для витрин. Так слои не дублируют логику качества.

### 4.6. Границы значений закреплены констрейнтами

**Решение:** в фактах есть `CHECK (low > 0 AND high >= low AND close > 0)`,
в `dim_date` - проверки диапазона `date_key`, месяца и квартала.

**Почему:** констрейнты ловят ошибки трансформации на уровне БД, а не только в
тестах, и документируют ожидаемые границы данных.

## Этап 5. Слой mart: витрины

### 5.1. Витрины денормализованы и пересчитываются upsert'ом

**Решение:** в `mart.stock_returns`, `mart.index_compare` и `mart.daily_movers`
поля `secid`/`boardid` продублированы; запись идёт upsert'ом по естественным
ключам (`(security_key, date_key)`, `(index_code, security_key, date_key)`,
`(date_key, security_key)`).

**Почему:** витрины должны читаться аналитиком без джойнов, а типовая
стратегия «delete+insert за период» здесь не нужна: бизнес-ключ строки
не меняется, поэтому upsert проще и безопаснее.

### 5.2. Метрики считаются по всей истории core, а пишутся за период

**Решение:** `build_stock_returns` читает весь `core.fact_daily_prices`,
считает скользящие окна по полной истории, но записывает строки только за
запрошенный период.

**Почему:** `LAG`, скользящее среднее, волатильность и накопленная доходность
на первой дате периода опираются на предыдущие дни. Если читать только период,
метрики на его начале были бы пустыми и неверными.

### 5.3. Нет данных - это NULL, а не 0

**Решение:** при отсутствии `prev_close`, пропуске внутри окна, неполном окне
или нулевом знаменателе метрика равна `NULL`; ноль используется только для
реального нулевого изменения или нулевой волатильности.

**Почему:** «нет данных» и «изменение 0%» - разные вещи; смешение делает
аналитику неверной. Правило явно описано в `include/mart_rules.py`.

### 5.4. Окна: полное окно и выборочное СКО

**Решение:** `ma_5`/`ma_20` появляются только при полном окне (5 и 20 дней),
волатильность - выборочное стандартное отклонение (`n - 1`) дневных
доходностей окна. Так как первый день истории не имеет доходности,
`volatility_20_pct` становится доступной на 21-м торговом дне.

**Почему:** это стандартные определения, а требование полного окна не даёт
сравнивать «среднее по 3 дням» со «средним по 20 дням» под одним именем.

### 5.5. Накопленная доходность отсчитывается от первой цены бумаги

**Решение:** `cumulative_return_pct` считается от первой доступной цены
закрытия бумаги в core, поэтому её первый день равен 0; при отсутствии
базовой цены или нулевой базе метрика равна `NULL`.

**Почему:** база должна быть одна и та же для всех дней бумаги, иначе метрика
зависит от окна запуска и перестаёт быть сопоставимой между запусками.

### 5.6. Ранжирование с равными значениями

**Решение:** `return_rank` в `mart.daily_movers` считается как
«1 + число бумаг со строго большей доходностью»; при равенстве ранги
совпадают, и флаги `is_best_of_day`/`is_worst_of_day` могут стоять у
нескольких бумаг дня.

**Почему:** это конкурентное ранжирование (как `RANK` в SQL); оно не даёт
произвольного порядка среди равных значений.

### 5.7. Витрина сравнения содержит только вычислимые дни

**Решение:** `mart.index_compare` соединяет `mart.stock_returns` и
`core.fact_daily_index` по `date_key` (INNER JOIN) и отбрасывает дни с
неизвестной доходностью (`NULL`).

**Почему:** первый торговый день периода без `prev_close` не даёт ни
доходности бумаги, ни доходности индекса - сравнивать там нечего, строка
была бы шумом.

## Этап 6. Слой audit: проверки качества данных (DQ) и свежесть

### 6.1. DQ отделён от слоёв данных: audit.dq_run + audit.dq_check

**Решение:** схема `audit` содержит две таблицы. `audit.dq_run` - один запуск
`scripts/run_dq.py` за период (статус `running`/`passed`/`failed`, счётчики
`checks_total`/`checks_passed`/`checks_failed`, время); `audit.dq_check` - одна
проверка внутри запуска (имя, слой, таблица, описание, статус
`passed`/`failed`/`error`, число проблем, порог, детали).

**Почему:** агрегат по запуску нужен для быстрого просмотра и мониторинга, а
детализация по проверкам - чтобы понять, что именно упало. Разделение на два
уровня не даёт смешивать итог запуска с отдельными правилами.

### 6.2. Проверка - это одно число, порог отдельно

**Решение:** каждая проверка - параметризованный SQL-запрос, возвращающий
число проблемных строк (или единиц проблемы). Проверка проходит, если это
число не превышает `max_allowed` (по умолчанию 0). Список проверок и логика
вывода статуса - чистые функции в `include/dq_rules.py`; выполнение и запись -
в `include/dq_checks.py`.

**Почему:** единый контракт («SQL -> число -> статус по порогу») позволяет
добавлять проверки без правки раннера и держать правила покрытыми
оффлайн-тестами (без psycopg2 и без БД).

### 6.3. Падение DQ останавливает пайплайн

**Решение:** `scripts/run_dq.py` возвращает код 1, если упала хотя бы одна
проверка. В DAG задача `run_dq` идёт последней (`load_raw >> build_stg >>
build_core >> build_mart >> run_dq`), поэтому ненулевой код завершает задачу
ошибкой.

**Почему:** качество данных - часть пайплайна, а не отчёт для галочки. Если
данные не проходят проверку, дальше продвигать их нельзя; Airflow помечает
задачу как failed и останавливает цепочку, а причина остаётся в
`audit.dq_check`.

### 6.4. Ошибка самой проверки не роняет весь запуск

**Решение:** если SQL проверки не выполнился (ошибка БД, опечатка в запросе),
проверка получает статус `error` и записывается с текстом ошибки; остальные
проверки продолжают выполняться. Статус `error` считается упавшим для итога
запуска.

**Почему:** одна сломанная проверка не должна скрывать результаты остальных.
Ошибка видна в `audit.dq_check.details`, а итоговый статус запуска остаётся
`failed`, то есть пайплайн всё равно останавливается.

### 6.5. Проверка свежести по журналу meta.load_run

**Решение:** `meta.freshness` - представление над `meta.load_run`: по каждой
таблице последний успешный прогон, последняя дата `date_to`, число упавших и
всего прогонов. Проверки `freshness_*` в DQ берут `max(loaded_at)` таблицы
слоя и сравнивают возраст с порогом (по умолчанию 720 ч, переменная
`DQ_FRESHNESS_MAX_HOURS`).

**Почему:** без отметки о свежести витрина может молча устареть. Порог сделан
щедрым (30 суток) осознанно: проект запускается вручную и бэкфиллом, поэтому
данные за старые периоды не должны валить проверку - цель сигнализировать о
«давно не обновляли», а не запрещать исторические прогоны.

### 6.6. Ограничение согласованности счётчиков dq_run

**Решение:** `audit.dq_run` допускает несведённые счётчики только в статусе
`running` (`status = 'running' OR checks_passed + checks_failed = checks_total`).

**Почему:** запись открывается до прогона проверок, когда `checks_passed` и
`checks_failed` ещё равны нулю; строгий вариант ограничения падал уже на
вставке. После завершения статус меняется, и сумма обязана сойтись с
`checks_total`.

## Этап 7. Документация под портфолио и гигиена репозитория

### 7.1. Bulk-загрузка истории скриптами, а не backfill DAG по одному дню

**Решение:** историю за длинный период заливают скриптами слоёв
(`load_raw.py -> build_stg.py -> build_core.py -> build_mart.py -> run_dq.py`),
которые принимают весь период сразу. Ежедневный DAG остаётся для регулярного
пополнения по одной дате.

**Почему:** обращение к ISS идёт одним проходом с пагинацией, а запись в БД -
пачками; при backfill Airflow создаёт отдельный DAG-run на каждый день, то есть
сотни задач и транзакций на историю в несколько лет. Результат у обоих путей
одинаков (оба идемпотентны), но bulk-скрипты на порядок дешевле по накладным
расходам оркестратора.

### 7.2. Один активный прогон DAG: max_active_runs=1

**Решение:** у DAG `moex_dwh_daily` выставлено `max_active_runs=1`.

**Почему:** слои пишут в одни и те же таблицы и обновляют одни и те же строки;
параллельные прогоны за пересекающиеся периоды конкурировали бы за блокировки и
давали бы лишнюю нагрузку на DWH и ISS. Последовательный запуск по одному
активному прогону убирает эту конкуренцию.

### 7.3. Локальные порты разведены со вторым стеком, container_name убран

**Решение:** локально в `.env` заданы `AIRFLOW_WEB_PORT=8081`,
`AIRFLOW_PG_HOST_PORT=5436`, `DWH_PG_HOST_PORT=5433`. В `docker-compose.yml`
нет `container_name`; в командах используется `docker compose exec <service>`
по имени сервиса, контейнеры получают префикс проекта (`moex_iss-`).

**Почему:** на машине параллельно работает стек `Mteo_Weather_AirFlow`,
который занимает 8080 и 5434. Общие порты по умолчанию и жёсткие
`container_name` давали конфликты привязок и имён; разведение портов и отказ от
фиксированных имён позволяют двум стекам жить одновременно. Значения по
умолчанию в compose безопасны для чистой машины.

### 7.4. Секреты - только в .env, в репозиторий попадает лишь .env.example

**Решение:** учётные данные и ключи (`FERNET_KEY`, пароли БД, пароль админа)
читаются из `.env`; сам `.env` в `.gitignore`. В репозитории - только
`.env.example` со значениями-заглушками, а `.venv`, `__pycache__`, `dist` и
логи также игнорируются.

**Почему:** исключает утечку секретов в git. Запуск с чистого клона работает
через `copy .env.example .env` без ручной правки обязательных значений.
